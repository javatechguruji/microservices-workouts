# Grafana walkthrough: metrics → traces → logs

Use this guide to investigate an order stuck in `CREATED` after stopping inventory-service.
It covers a successful order first, the failure, and recovery. For the concepts,
see [Logs, metrics and tracing](01-logs-metrics-and-tracing.md).

## 1. Open Grafana

1. Open [Grafana](http://localhost:3000).
2. Sign in with the local defaults:
   - **Username:** `admin`
   - **Password:** `WorkoutsGrafana-Local-2026!`
3. If you changed `GRAFANA_ADMIN_PASSWORD` or the saved Grafana password, use that instead.

No new dashboard or data source should be needed. This project automatically
configures **Prometheus** for metrics, **Tempo** for traces, and **Loki** for logs.

If you want to check the connections, open the side menu → **Connections → Data
sources**. All three should be listed. Open a source and use **Save & test** if
available. The addresses such as `http://loki:3100` are Docker network addresses;
do not replace them with your browser's `localhost` address.

## 2. Prepare the applications

1. Run shared infrastructure and the frontend as described in the
   [setup guide](../infra-setup/observability-implementation-guide.md).
2. Start all nine microservices, including inventory-service, using their IntelliJ
   **observable** run configurations. These attach the OpenTelemetry Java agent.
3. If the services were running before the logging improvements, restart them to
   load the new code. Old log entries will not gain the new fields.
4. Keep the default INFO level for this exercise. Checkout failures are WARN-level
   events and do not require DEBUG. To see routine reads and outgoing request-start
   details, add `APP_LOG_LEVEL=DEBUG` to a service's IntelliJ environment variables
   and restart that service.
5. Open the application at [localhost:5173](http://localhost:5173) and sign in.

Use an isolated local learning run. Local and stage share databases and Kafka
consumer groups, so avoid the failure exercise while another environment is using them.

## 3. See a successful order first

1. With inventory running, open the Shop page and reload it a few times.
2. Add an available product to the cart and place an order.
3. Record the **order ID**, **amount**, and approximate **time**.
4. Open **My orders** and wait for the order to reach `CONFIRMED`.
   The intermediate `CREATED`, `RESERVED`, and `PAID` states may pass too quickly
   to see in the frontend.
5. Wait roughly **30–60 seconds** for measurements to reach Grafana.

The browser may receive `202 Accepted` before payment and stock reservation finish.
That response means the order was accepted for processing, not that it is complete.

## 4. Metrics: learn the dashboard

1. Open the side menu → **Dashboards**, then select
   **Commerce — requests, JVM and checkout**. Or open the
   [Commerce dashboard directly](http://localhost:3000/d/commerce-overview).
2. At the top, set **Environment = local** and **Service = All**.
3. In the top-right time picker, choose **Last 15 minutes**.
4. Click **Refresh**. Optionally select a refresh interval, such as 10 seconds.
5. Scroll through these panels:

| Panel | What to look for |
| --- | --- |
| HTTP request rate | Traffic generated by browsing and placing orders. |
| HTTP p95 latency | How long the slower requests take. With little traffic, this can be empty or unstable. |
| HTTP 5xx ratio | The share of HTTP requests returning server errors. An empty series is not automatically a broken dashboard. |
| Pending checkouts | Orders still waiting for the worker to finish. A completed order may already show zero. |
| Checkout attempt failures | Failed attempts per second over a five-minute window, not the number of unique failed orders. |
| Business metric refresh age | Seconds since the last successful database count. A rising age means the backlog count may be stale. |
| Unpublished outbox rows | Saved events still waiting to be sent to Kafka. |

You can select **order-service** to focus on checkout, then **gateway-service** to
inspect errors forwarding calls to inventory. Keep the same time range when switching views.

## 5. Create the inventory failure

1. While inventory-service is still running, add an available item to the cart.
2. Stop **only inventory-service** in IntelliJ.
3. Submit the checkout from the frontend. Note its order ID, amount and time.
4. If the order is accepted, check its details. It should remain in `CREATED` while
   the worker cannot reserve inventory. Inspect the actual browser response if
   checkout itself is rejected; do not assume every submission was accepted.
5. Wait 30–60 seconds, then refresh the Commerce dashboard.
6. Look for pending work and failed checkout attempts. Check Gateway's HTTP errors too.

A single waiting order is enough for this exercise. It will not trigger the
configured backlog alert, which requires more than 10 pending checkouts for five minutes.
The checkout HTTP request can succeed with `202` while the later worker's call fails.

## 6. Traces: find where the call failed

1. Open the side menu → **Explore**, or use [Explore directly](http://localhost:3000/explore).
2. In the data-source dropdown at the top, select **Tempo**.
3. Set **Last 15 minutes**, or choose an absolute time range around the failed order.
4. Choose the **TraceQL** query editor. Depending on the UI, this may appear as the
   **TraceQL** tab or a query-type selection.
5. Enter the following and click **Run query**:

```traceql
{ resource.service.name = "order-service" }
```

6. Open a recent trace near the time the worker retried. Search results can include
   unrelated reads and scheduled work, so inspect the recorded operations.
7. Expand the trace's service rows and spans in the timeline.
8. Find an HTTP call whose attributes show `/api/inventory/reservations`.
9. Click that span. Inspect its service name, duration, error status and HTTP status
   or error attributes when present.
10. Copy the **Trace ID** shown in the trace header. Keep it for the log search.

To narrow the results to failed spans in order-service, try:

```traceql
{ resource.service.name = "order-service" && status = error }
```

If that returns nothing, use the broader query again, or search Gateway errors:

```traceql
{ resource.service.name = "gateway-service" && status = error }
```

These queries use Tempo's [TraceQL query syntax](https://grafana.com/docs/grafana/latest/datasources/tempo/query-editor/traceql-query-examples/).

### What the trace should explain

The order worker calls Gateway, and Gateway attempts to reach inventory-service.
Inspect the recorded error and status instead of assuming a particular status code.
**A stopped inventory process cannot create a receiving span**, so you may see the
failure on the calling service or Gateway rather than an inventory span.

The original checkout API request and the later worker run can have different
Trace IDs. Our database does not save the original trace context for the worker.
Use the order ID to connect these stages.

A metric chart covers many requests. Opening a chart does not necessarily open the
exact trace for your order. Start with service and time, then confirm the order in
its logs. If you cannot identify the right trace, use the order-log search below
and follow its **TraceID** link back to Tempo.

## 7. Logs: read the matching failure

### Find the order's failure entries

1. In **Explore**, switch the data source to **Loki**.
2. Keep the time range around the failed order.
3. Select **Code** instead of Builder in the query editor.
4. Paste this query and click **Run query**:

```logql
{service_name="order-service"} |= "checkout.dependency.failed"
```

5. Click a log row to expand its message and fields.
6. Look for **orderId**, **amount**, **state**, **dependency**, **status**,
   **attempt**, **retryInSeconds**, and **nextAction** in the message's `data` object.
   Field grouping can vary between structured metadata and the displayed message.

Example only:

```text
event=checkout.dependency.failed data={"orderId":42,"amount":22.50,"state":"CREATED","dependency":"inventory-service","status":503,"attempt":3,"retryInSeconds":10,"nextAction":"RETRY",...}
```

This says order 42 is still waiting for inventory and will retry after 10 seconds.
It does not mean payment already failed: the order has not reached the payment step.

### Filter by your order ID

Replace `42` with your order ID:

```logql
{service_name="order-service"} |= "checkout.dependency.failed" |= "\"orderId\":42,"
```

You can also filter by amount, using the exact number formatting shown in the log:

```logql
{service_name="order-service"} |= "checkout.dependency.failed" |= "\"amount\":22.50,"
```

Prefer the order ID: different customers can place orders for the same amount.
Addresses, passwords, tokens and full personal payloads are intentionally omitted.

### Match the Trace ID from Tempo

Replace `PASTE_TRACE_ID` with the ID copied from the failed trace:

```logql
{service_name="order-service"} | trace_id="PASTE_TRACE_ID"
```

To include Gateway logs from the same trace:

```logql
{service_name=~"order-service|gateway-service"} | trace_id="PASTE_TRACE_ID"
```

Here `trace_id` is a field filter after the pipe, not a stream label inside `{}`.
This is the pattern used for [trace/log correlation](https://grafana.com/docs/grafana/latest/datasources/tempo/configure-tempo-data-source/trace-correlations/).

Look for `http.client.completed` or `http.client.failed` in order-service and
`http.server.completed` in Gateway. Read the path, target service, status and safe
failure description to distinguish a rejected response from a connection problem.
There will be no fresh inventory logs while its process is stopped.

### Use the links between logs and traces

- **Logs → trace:** Expand a log row, find **TraceID**, and click its Tempo link.
- **Trace → logs:** Open a span's details and click its logs/document icon if shown.
  This opens the configured Loki query, often in a split view. Grafana documents
  this under [Traces in Explore](https://grafana.com/docs/grafana/latest/visualizations/explore/trace-integration/).
- If the generated view is empty, use the manual queries above and widen the time
  range. A span's log link filters by that span's service; an order retry log is in
  order-service, not necessarily the service of the span you selected.

## 8. Restart inventory and confirm recovery

1. Restart inventory-service with its **observable** IntelliJ run configuration.
2. Allow the next retry, normally after about 10 seconds, plus time for processing.
3. Open the same order in the frontend and watch it progress toward `CONFIRMED`.
4. In Loki, search for its state changes:

```logql
{service_name="order-service"} |= "checkout.state.changed" |= "\"orderId\":42,"
```

5. Look for `CREATED → RESERVED → PAID → CONFIRMED` across the entries. These may
   have different Trace IDs because they run as separate worker steps.
6. Refresh the dashboard after 30–60 seconds. Pending work should fall as orders
   finish. The underlying failure counter does not decrease; its five-minute rate
   takes time to settle back down.
7. Open a recovery trace to inspect successful inventory calls. Unlike during the
   outage, inventory can now record its own spans.

## 9. If a view is empty or confusing

| Symptom | Check |
| --- | --- |
| Dashboard is missing | Look for **Commerce — requests, JVM and checkout** or use the direct link. Check Grafana provisioning mounts in Docker Compose if it is absent. |
| Prometheus, Loki or Tempo is missing | Check **Connections → Data sources** and the running Compose infrastructure. Provisioning should supply them; no manual dashboard creation is required. |
| No recent data anywhere | Confirm the services are running with `-javaagent`, then check the Collector endpoint and time range. |
| Old logs appear, but new labeled events do not | Restart with the rebuilt code, generate a new request/retry, and select a recent time range. |
| Metrics are empty immediately after a request | Wait 30–60 seconds. Check **Environment = local** and **Service = All**. |
| Checkout chart changes, but order-service has no HTTP 5xx | The API may have returned `202`; inspect the worker's outbound call and Gateway instead. |
| Error-only trace query returns nothing | Search all order-service traces first. Check time, service and whether the operation has an error-marked span. |
| A trace has no inventory span | Expected while inventory is down: investigate the caller/Gateway error. |
| Log has no Trace ID | Startup logs and work outside an active trace may not have one. Use order/event IDs where available. |
| A trace has no matching logs | Not every span produces a log. Search by service/time/order ID and check whether DEBUG is needed for routine reads. |
| Amount search finds nothing | Match the displayed decimal formatting, or search by order ID instead. |
| Pending count is zero but the order screen looks stuck | Check the order's latest state and the **Business metric refresh age**; a stale reading is not proof of completion. |

Record the order ID, failure time, Trace ID and error details when you find the
problem. Those four items let you return to the same evidence later.
